# 名称伪装和刹车增强不稳定性分析报告

**文档版本**：v1.0  
**创建日期**：2026年1月26日  
**分析人员**：AI 助手  
**文档目的**：供高手深度分析验证，确定不稳定性根本原因

---

## 📋 问题概述

MA_FH5Trainer_CN 项目中，名称伪装和刹车增强功能存在"时而有效、时而无效"的不稳定现象。

**关键特征**：
- 功能初始化成功（AoB 扫描和 Detour 创建都正常）
- 运行时出现间歇性失效
- 不是签名失效问题（签名失效时功能完全无法初始化）

---

## 🔍 分析方法

通过深度代码分析，排除了签名失效的可能性，重点分析运行时状态管理和游戏行为对功能的影响。

**分析范围**：
- 名称伪装实现机制（`MiscCheats.cs`）
- 刹车增强实现机制（`Handling.Automation.cs`）
- Detour 创建和管理（`Memory.cs`）
- 内存写入机制（`Write.cs`）
- Bypass 机制（`Bypass.cs`）

## 🎯 名称伪装不稳定性分析

### 1. 功能架构

```
用户启用名称伪装
  ↓
AoB 扫描定位名称函数地址 (_nameAddress)
  ↓
Bypass.DisableCrcChecks() 禁用 CRC 检查
  ↓
CheatNamePtr() 扫描名称数据指针链
  ↓
CreateDetour() 创建 Hook：
  - VirtualAllocEx 分配 0x1000 字节内存 (NameDetourAddress)
  - 内存保护设置为 ExecuteReadwrite (0x40)
  - 写入 Hook 代码（检查全局标志后返回自定义名称）
  - 原始代码替换为 JMP 指令跳转到 Hook
  ↓
写入启用标志 (offset + 0x55)
  ↓
写入名称数据 (offset + 0x56)
  ↓
完成
```

### 2. 关键代码位置

| 文件 | 行号 | 功能 |
|------|------|------|
| `MiscCheats.cs` | 48-70 | `CheatName()` - 名称伪装初始化 |
| `MiscCheats.cs` | 85-101 | `CheatNamePtr()` - 指针链扫描 |
| `Misc.xaml.cs` | 51-58 | 写入启用标志和名称数据 |
| `Bypass.cs` | 24-42 | `DisableCrcChecks()` - 禁用 CRC 检查 |
| `Memory.cs` | 243-285 | `CreateDetour()` - 创建 Hook |

### 3. 不稳定性根本原因

#### 🔴 **问题 1：Hook 代码可能被游戏覆盖**

**代码位置**：`MiscCheats.cs:78`
```csharp
NameDetourAddress = GetInstance().CreateDetour(_nameAddress, asm, 7);
```

**问题分析**：
- Hook 代码通过 `CreateDetour()` 写入游戏内存
- 游戏可能在以下场景覆盖 Hook 代码：
  1. **场景切换**：进入/离开比赛、切换地图时重新加载模块
  2. **内存优化**：游戏内存管理器释放或移动未使用的内存区域
  3. **反作弊扫描**：反作弊系统检测到异常代码段并恢复原始代码

**影响**：
- Hook 代码被覆盖后，名称显示函数执行原始代码
- 不再返回自定义名称
- 功能失效但用户不知道原因

**验证方法**：
1. 在 Hook 代码位置设置内存断点
2. 监控游戏是否重新写入该内存区域
3. 检查 Hook 代码是否被修改

#### 🔴 **问题 2：启用标志只写入一次**

**代码位置**：`Misc.xaml.cs:51`
```csharp
GetInstance().WriteMemory(MiscCheatsFh5.NameDetourAddress + 0x55,
```

  3. **多人游戏同步**：服务器强制同步玩家状态
  4. **照片模式**：进入/退出照片模式时重置

**影响**：
- 标志被重置为 0 后，Hook 代码即使完整也不生效
- 用户需要重新切换开关才能恢复功能

**验证方法**：
1. 监控 `NameDetourAddress + 0x55` 的值
2. 在不同游戏场景下检查该值是否被重置

#### 🔴 **问题 3：Bypass 可能失效**

**代码位置**：`Bypass.cs:24-42`
```csharp
public async Task DisableCrcChecks()
{
    // 修改 CRC 检查代码：4C 3B EF → 48 39 FF
    GetInstance().WriteArrayMemory(CallAddress, new byte[] { 0x48, 0x39, 0xFF });
    CallAddress += 3;
}
```

**问题分析**：
- Bypass 修改 CRC 检查函数后没有持续维护
- 游戏可能在以下场景恢复 CRC 检查：
  1. **代码完整性验证**：游戏定期验证代码段的完整性
  2. **反作弊更新**：反作弊系统检测到 CRC 检查被禁用并恢复
  3. **游戏重启**：Bypass 修改在游戏重启后失效

**影响**：
- Bypass 失效后，游戏的完整性校验检测到 Hook 代码
- 恢复原始代码，导致 Hook 失效

**验证方法**：
1. 检查 `Bypass.CallAddress` 的值（应 > 3）
2. 监控 CRC 检查代码是否被恢复
3. 记录 Bypass 失效的时机

## 🎯 刹车增强不稳定性分析

### 1. 功能架构

```
用户启用刹车增强
  ↓
EnsureLocalPlayerDetourAsync() 确保 Detour 存在
  ↓
创建定时器 (33ms 循环)
  ↓
每 33ms 读取 LT 扳机值
  ↓
计算刹车强度 (CalculateBrakeAssist)
  ↓
写入 Detour 数据区：
  - BrakeHackEnabled (byte) @ offset + 0x1EB + 9
  - BrakeHackBoost (float) @ offset + 0x1EB + 10
  ↓
游戏主循环调用 Detour 代码
  ↓
Detour 代码检查 BrakeHackEnabled
  ↓
如果为 1，使用 BrakeHackBoost 修改刹车参数
```

### 2. 关键代码位置

| 文件 | 行号 | 功能 |
|------|------|------|
| `Handling.Automation.cs` | 367-402 | `RunBrakeAssistAutoAsync()` - 刹车增强主循环 |
| `Handling.Automation.cs` | 416-435 | `EnsureLocalPlayerDetourAsync()` - Detour 重建 |
| `Handling.Brake.cs` | 35-61 | `BrakeAssistSwitch_OnToggled()` - 开关切换 |
| `CarCheats.cs` | 47-133 | `CheatLocalPlayer()` - 创建 LocalPlayerHook |
| `BrakeCurves.cs` | 33-78 | `CalculateBrakeAssist()` - 刹车曲线计算 |

### 3. 不稳定性根本原因

#### 🔴 **问题 1：Detour 重建导致状态丢失（最严重）**

**代码位置**：`Handling.Automation.cs:448-452`
```csharp
private async Task EnsureLocalPlayerDetourAsync(CancellationToken token)
{
    if (_carCheats.LocalPlayerHookDetourAddress > UIntPtr.Zero)
    {
        return;  // Detour 已存在，跳过
    }

    // ... 重建 Detour ...

    // ⚠️ 问题：Detour 重建后强制写入默认值
    _memoryWriter.Write(_carCheats.LocalPlayerHookDetourAddress + CarCheatsOffsets.BrakeHackEnabled, (byte)0, false);
    _memoryWriter.Write(_carCheats.LocalPlayerHookDetourAddress + CarCheatsOffsets.BrakeHackBoost, 1f, false);
}
```

**问题分析**：
- Detour 重建时会强制写入 `BrakeHackEnabled=0` 和 `BrakeHackBoost=1.0`
- 如果刹车增强正在运行且 LT 按下，状态会被重置
- 用户需要释放 LT 并重新按下才能恢复刹车效果

**触发场景**：
1. **游戏重启**：游戏重启后 `LocalPlayerHookDetourAddress` 变为 0
2. **场景切换**：切换地图、进入比赛时，玩家实体可能切换
3. **车辆切换**：切换车辆时，LocalPlayer 指针可能改变

**影响**：
- Detour 重建后，刹车增强效果突然消失
- 用户体验极差，需要重新操作

**验证方法**：
1. 在 `EnsureLocalPlayerDetourAsync()` 设置断点
2. 监控 Detour 重建时机
3. 检查重建后刹车状态是否被重置

#### 🔴 **问题 2：写入频率不足**

**代码位置**：`Handling.Automation.cs:373`
```csharp
using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(33));  // 33ms ≈ 30Hz
```

**问题分析**：
- 修改器写入频率：33ms (30 Hz)
- 游戏主循环频率：可能 16ms (60 Hz) 或更快
- 游戏可能在两次写入之间重置刹车参数

**频率对比**：
| 写入源 | 频率 | 周期 |
|--------|------|------|
| 修改器写入 | 30 Hz | 33ms |
| 游戏主循环 | 60 Hz+ | 16ms 或更快 |

**问题**：
- 如果游戏在每帧开始时重置刹车参数
- 修改器在 33ms 后才重新写入
- 在这 33ms 内，刹车增强失效

**影响**：
- 刹车增强效果"时而有效"
- 在游戏重置参数的瞬间失效

**验证方法**：
1. 监控 `BrakeHackEnabled` 和 `BrakeHackBoost` 的值
2. 检查游戏是否在两次写入之间重置这些值
3. 测量游戏重置频率

#### 🔴 **问题 3：游戏在特定事件重置刹车参数**

**触发场景**：
1. **比赛开始**：游戏初始化新的车辆物理状态
2. **车辆切换**：游戏加载新的车辆参数
3. **碰撞事件**：严重碰撞后重置车辆状态
4. **场景切换**：切换地图、进入车库时重置参数
5. **多人游戏同步**：加入多人游戏时同步车辆状态

**影响**：
- 在这些场景下，游戏会重置刹车参数
- 修改器的值会被覆盖
- 功能失效直到下次写入

**验证方法**：
1. 在不同场景下监控刹车参数
2. 记录重置时机和频率
3. 确认重置是由游戏还是其他功能引起

#### 🔴 **问题 4：竞态条件**

**问题分析**：
- 多个定时器同时写入同一内存地址
- 所有 Handling 功能共享 `LocalPlayerHookDetourAddress`

**定时器列表**：
| 功能 | 定时器频率 | 写入偏移 |
|------|-----------|---------|
| 速度 | 33ms | VelEnabled, VelBoost |
| 轮速 | 16ms | WheelspeedEnabled, WheelspeedBoost |
| 刹车增强 | 33ms | BrakeHackEnabled, BrakeHackBoost |
| 超级刹车 | 33ms | StopAllWheelsEnabled |

**问题**：
- 同时启用多个功能时，写入时机可能重叠
- 某个功能的写入可能被另一个功能覆盖
- 导致功能失效

**影响**：
- 同时启用多个功能时，某些功能可能失效
- 快速切换功能时可能出现竞态

**验证方法**：
1. 同时启用多个功能
2. 监控所有写入操作
3. 检查是否存在写入冲突

## 💡 建议的修复方案

### 名称伪装修复方案

#### 方案 1：添加持续写入机制
```csharp
// 创建定时器持续写入启用标志和名称数据
using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(200));
while (await timer.WaitForNextTickAsync(token))
{
    if (NameDetourAddress > 0 && toggleSwitch.IsOn)
    {
        // 持续写入启用标志
        GetInstance().WriteMemory(NameDetourAddress + 0x55, (byte)1);
        
        // 持续写入名称数据
        var name = Encoding.Unicode.GetBytes(NameBox.Text);
        GetInstance().WriteArrayMemory(NameDetourAddress + 0x56, name);
    }
}
```

#### 方案 2：添加 Hook 完整性检查
```csharp
// 定期检查 Hook 代码是否被覆盖
private async Task<bool> VerifyHookIntegrity()
{
    var expectedBytes = new byte[] { /* Hook 代码 */ };
    var actualBytes = GetInstance().ReadArrayMemory(NameDetourAddress, expectedBytes.Length);
    if (!actualBytes.SequenceEqual(expectedBytes))
    {
        // Hook 代码被覆盖，重新写入
        GetInstance().WriteArrayMemory(NameDetourAddress, expectedBytes);
        return false;
    }
    return true;
}
```

#### 方案 3：添加 Bypass 持久化

## 🎯 结论

### 名称伪装不稳定性根本原因：
1. **Hook 代码可能被游戏覆盖**：游戏场景切换、反作弊扫描时覆盖
2. **启用标志只写入一次**：游戏重置后无法恢复
3. **Bypass 可能失效**：修改 CRC 检查后没有持续维护
4. **名称数据只写入一次**：多人游戏同步时被服务器覆盖
5. **无持续写入机制**：所有写入都是一次性操作

### 刹车增强不稳定性根本原因：
1. **Detour 重建导致状态丢失**（最严重）：重建时强制写入默认值
2. **写入频率不足**：33ms (30Hz) vs 游戏主循环可能 60Hz+
3. **游戏在特定事件重置刹车参数**：比赛开始、车辆切换、碰撞事件等
4. **竞态条件**：多个定时器同时写入同一内存地址
5. **写入失败无错误处理**：静默失败，无法追踪

### 关键洞察：
- **名称伪装**：静态问题 - Hook 代码和数据被游戏覆盖，没有持续维护
- **刹车增强**：动态问题 - Detour 重建丢失状态，写入频率跟不上游戏重置频率
