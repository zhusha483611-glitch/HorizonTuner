## 二、对报告定级的三处细化

### 2.1 `PhysicsMisc.cs:120` 是"失败恢复失败"，严重性略低于 S3

该分支仅在 `GravityDetourAddress <= 0`（重力注入**已失败**）时进入。后果链：注入失败 → 开关回弹 → 处理器第二次 `-=`（空操作）→ 处理器永不重新挂回 → **用户无法在同次会话重试**，需重启 App。

- 性质：可用性陷阱 + 故障叠加，**非运行时崩溃**。
- 报告将其与 S3（崩溃残留 patch）同列 P0。建议：**仍 P0**（一行修复、消除永久失活），但 S3 后果更重（可破坏游戏会话、游戏残留 patch），应为 **P0 之首**。

### 2.2 `Memory.cs:220` 负偏移 Bug 的"活/潜"未区分

方法签名 `IEnumerable<int> offsets` 允许负值，逻辑确实写反。但报告未展示**是否有调用方实际传入负偏移**：

- 若无调用传负值 → 潜伏 Bug（签名敞开口子，仍应修）。
- 若有 → 活 Bug，S4/HIGH 定级成立。

修复结论不变，但定级论据应补一句"已确认存在负偏移调用"或"当前潜伏，签名允许故必修"。落地前建议先 grep `FollowMultiLevelPointer` 调用点的偏移来源确认。

### 2.3 `MemoryPool` 语义被报告轻微混淆（最有价值的修正点）

报告建议"实现并接入 MemoryPool"以兑现 AGENTS.md 的"AoB 结果缓存"。但读 [MemoryPool.cs](../../MA_FH5Trainer/MA_FH5Trainer/Cheats/MemoryPool.cs) 实际实现：它是**原生内存块租借池**（`Rent`/`Return`/`ConcurrentBag<MemoryBlock>`，减少 `NativeMemory.Alloc/Free` 抖动），**不是"签名→地址"结果缓存**。

AGENTS.md 所说"AoB 扫描结果进 MemoryPool 缓存"描述的是后者。**即便把 MemoryPool 接入，也不满足 AGENTS.md 的承诺**——两者是不同设施。真正修法二选一：

- **(a)** 新建 `AoBResultCache`（签名→地址，进程会话级失效）——这才是 AGENTS.md 想要的；
- **(b)** 修正 AGENTS.md 措辞，承认 MemoryPool 是块池（且当前未启用），AoB 无结果级缓存。

报告的"实现并接入 MemoryPool"会把块池当结果缓存接上去，治标而错位。

## 三、报告漏连的两条因果链

### 3.1 `async void` 无 try/catch 与 S3 是同一条故障路径

WPF 中 `async void` 事件处理器抛出的未处理异常会冒泡到 `DispatcherUnhandledException`。而 S3 指出 [App.xaml.cs](../../MA_FH5Trainer/MA_FH5Trainer/App.xaml.cs) 的 `ReportException` 直接 `Environment.Exit(1)` 无 `Cleanup()`。所以：

```
WheelspeedSwitch_OnToggled 抛异常
  → 命中脆弱全局处理（ReportException → Environment.Exit(1)）
  → 无 Cleanup() 退出
  → 游戏残留 patch + 代码洞泄漏
```

报告把 `async void`（维度三 W6）与 S3（维度七）分列，未指出**修 S3 是 async-void 风险的力乘器**——注册 `ProcessExit` + best-effort `Cleanup()` 一处修复同时缓解两类问题。落地应**先 S3，async-void 的 try/catch 作为纵深防御**。

### 3.2 W6 关闭超时的隐藏前置：CancellationToken 链接纪律

报告给 W6 两个修法（`Task.WhenAll` / 提超时到 5000ms），但未追问：8 个循环的 token 是否都正确 link 到了 `ShutdownCoordinator` 的根 token？若有循环未 link，`WhenAll` 也救不了——该循环不会响应取消。这是 W6 的隐藏前置，落地时一并核查 token 链接，而非只改 await 形态。

## 四、报告"治症不治因"的两处

### 4.1 七线程竞态：`SemaphoreSlim` 是症状层

7 个循环各自调 `EnsureLocalPlayerDetourAsync` 的根因是：**每个特性（velocity/wheelspeed/brake/jump…）各跑独立轮询循环，各自重复"确保本地玩家 detour"这一共享前置**。加信号量能消除对 `CheatLocalPlayer()` 的并发重建，正确且应做；但更彻底的是把"确保 detour"抽成**共享的 detour 生命周期服务**，各循环订阅其就绪状态而非各自重确保。落地时信号量作短期止血，共享服务作中期目标。

### 4.2 Handling DI 接线：略过 WPF 视图激活机制

[Handling.xaml.cs](../../MA_FH5Trainer/MA_FH5Trainer/Views/SubPages/SelfVehicle/Handling.xaml.cs) 是 WPF 页面，由导航构造，**默认不经 DI 容器解析其构造函数**。把 15-19 行的 `new` 换成 `App.GetRequiredService<T>()` 方向正确，但落地需要**一个 DI 感知的视图工厂/导航服务**（或接受服务定位器模式）。报告把这写成"改 5 行 + 补注册"偏轻——实际牵涉视图激活路径，工作量被低估。

## 五、关于"90% 未测试"

数字大致成立，但**可操作缺口远小于 90%**。未测代码分两类：

- **本质难测**：Memory 引擎、Cheats 的 P/Invoke 路径——需真实游戏进程，单测性价比低。报告已用"接缝到位（FakePrivilegeApi/FakeSqlCheat/FakeCheat）"承认这部分靠接缝隔离。
- **可测而未测**：Facade 实现、配置 JSON 往返、`VelocityPresetNaming`、`GameVerPlat` 解析——纯/近纯，是高价值缺口。

报告在建议里**确实指向了正确的可测面**，结论正确；但"90%"的框法会误导读者追求覆盖率数字。落地按"先 Facade + 配置往返 + 纯 Model"推进，约 15–20% 即可覆盖大部分可测高价值面。

## 六、落地顺序建议

报告的 P0–P3 总表方向正确，本文仅调整**顺序与组合**：

1. **S3 崩溃清理**（[App.xaml.cs](../../MA_FH5Trainer/MA_FH5Trainer/App.xaml.cs)）— 注册 `ProcessExit` + `TaskScheduler.UnobservedTaskException`，best-effort `Cleanup()`/`DisconnectFromGame()`，超时保护。**力乘器**：同时压住 S3 与 async-void 两类风险，性价比最高，应**最先做**。
2. **`PhysicsMisc.cs:120`** — 第二个 `-=` 改 `+=`，一行。
3. **`Memory.cs:220`** — 负偏移改 `finalAddress -= (nuint)(-offset);`（先 grep 调用点确认活/潜）。
4. **SQL 参数化**（[Sql.cs](../../MA_FH5Trainer/MA_FH5Trainer/Cheats/Sql.cs)）— 参数化或白名单。
5. **P1 项**：`EnsureLocalPlayerDetourAsync` 加 `SemaphoreSlim`；`StopAllAutomationAsync` 改 `Task.WhenAll` + 核查 token 链接；CI 覆盖率 + 格式门禁；MemoryPool 决策（建 `AoBResultCache` 或修 AGENTS.md）。
6. **P2/P3**：按报告总表推进，DI 接线配视图激活改造，竞态根治配共享 detour 服务。

P0 四项均为局部修复（一行至数十行），风险隔离，建议立即落地。
