## 现象解释（为什么只在结算生效）
- 当前名称伪装只 Hook 了一个函数入口（`MiscCheats.CheatName()` 用单个 AoB 定位 `_nameAddress` 后 `CreateDetour(..., 7)`），并且 detour 内部还带“只对本地玩家命中才替换”的判断逻辑（见 [MiscCheats.cs](file:///d:/AI/MA_FH5Trainer_CN-main/MA_FH5Trainer/MA_FH5Trainer/Cheats/MiscCheats.cs#L45-L102)）。
- 比赛中“排名/排行榜/HUD”显示的名字**很可能走的是另一条渲染/数据路径**（例如不同的 UI 文本格式化函数、网络同步的 Gamertag 数据等），所以结算页能命中你当前 Hook，但比赛排名不命中或命中后被逻辑过滤掉。

## 目标
- 判断“比赛排名不生效”的根因属于哪一类：
  1) **同一个 Hook 点被调用了，但 detour 判断没命中（只走原逻辑）**
  2) **比赛排名根本不走这个 Hook 点（需要新增第二个 Hook 点）**

## 实施方案（以最小风险拿到确定结论）
### 1) 给名称伪装加入可观测诊断（用于验证是否命中）
- 在 Name detour 的数据区新增只读统计字段：
  - `TotalCalls`（detour 被调用次数）
  - `SpoofTaken`（走“返回伪装名”分支次数）
- 在 UI（Misc 页面与 Handling 快捷区）显示这两个计数，以及当前 `Enabled`、当前写入的 name buffer 前若干字节的 hash（不直接打印名字内容）。
- 预期：
  - 如果比赛中打开排名时 `TotalCalls` 不增长 → **排名不走这个 Hook 点**。
  - 如果 `TotalCalls` 增长但 `SpoofTaken` 不增长 → **detour 内判断条件不适配排名场景**。

### 2) 提供一个“强制伪装（不做本地玩家判断）”的调试开关
- 增加一个仅用于排查的模式：`ForceSpoof`（当开启时，只要 `Enabled=1` 就直接返回伪装名）。
- 用它快速判定：
  - 若开启后比赛排名仍不变 → **必须新增第二个 Hook 点**。
  - 若开启后比赛排名可变 → **只需改进/扩展本地玩家识别逻辑**。

### 3) 若确定需要第二个 Hook 点：扩展为“多 Hook 名称伪装”
- 新增一个 `CheatNameInRace()`（或多签名集合）：
  - 新增 AoB/扫描策略用于定位“比赛排名名字格式化/渲染”相关函数。
  - 对每个命中地址都创建 detour，并复用同一份 name buffer/开关。
- 由于仓库内目前没有 leaderboard/ranking 相关关键词线索，我会让实现支持：
  - 你后续提供 CE 地址/模块名/字节特征码时可直接填入签名列表（无需再大改框架）。
