## 现象与根因假设
- 你看到“最高每秒三十多次”很像 **30Hz/33ms** 的节拍。
- 当前自动循环（速度/轮速/刹车等）是从 WPF 事件触发启动的 async 方法；如果内部 `await` 没有 `ConfigureAwait(false)`，续体会回到 **UI Dispatcher 同步上下文**，循环节拍就会受 UI 帧率/消息泵影响，常见上限就是 30Hz。
- 另外 `Mem.WriteMemory` 默认每次写都会 `VirtualProtectEx` 切保护（removeWriteProtection=true），在 60Hz 连续写时会造成额外开销，进一步降低频率。

## 优化目标
- 让“注入/写入循环”稳定在接近 60Hz（理论 62.5Hz），并且不被 UI 卡顿拖慢。
- 保持现有功能行为不变（仍按 RT/LT 门控），只优化调度与写入开销。

## 实施方案
### 1) 彻底把自动循环从 UI 线程剥离
- 启动循环时改为 `Task.Run` 执行（或在循环内部所有 `await` 使用 `ConfigureAwait(false)`），确保循环续体始终在 ThreadPool。
- 对 `EnsureLocalPlayerDetourAsync`、`Task.Delay` 等 await 统一 `ConfigureAwait(false)`，避免回到 Dispatcher。
- 涉及 UI 的更新（例如诊断文本）统一改成低频（200ms）在单独的 UI 更新点做，不在高频循环里 `Dispatcher.InvokeAsync`。

### 2) 用更稳定的节拍器替代“Delay(16)”（可选但推荐）
- 用 `PeriodicTimer(TimeSpan.FromMilliseconds(16))` 驱动循环，减少漂移和累积误差。
- 记录实际 tick 间隔（Stopwatch）用于诊断“为什么只有 30Hz”。

### 3) 降低每次写入的系统调用成本
- 对 detour 变量区写入（`LocalPlayerHookDetourAddress + offsets`）改用 `WriteMemory(..., removeWriteProtection:false)`，跳过每次 `VirtualProtectEx`。
- 对 Boost/Limit/Mode 仅在值变化时写（或低频写），把高频写聚焦在 `Enabled`/必要字段。

### 4) 增强可观测性（定位是否仍被 detour 调用频率限制）
- 在现有状态栏基础上增加：
  - 自动循环真实 tick/秒
  - 写入失败/异常计数（仅计数不弹窗）
- 这样你能一眼看出“是循环跑不快”还是“detour 本身调用慢”。

## 验证方式
- `dotnet build` 确认编译通过。
- 运行后在 Handling 顶部状态栏观察：
  - tick/秒是否稳定接近 60
  - 速度写入/秒是否接近 tick/秒（在 RT 按住且过阈值时）
