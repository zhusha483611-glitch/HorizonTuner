## 现象解释（先把原因讲清）
- 现有三种模式的“限速”更像是“到达阈值后停止注入/停止加成”，并不等价于“强制把车拉到该速度”。当车辆本身在高车速下受到空气阻力/齿比/牵引限制时，如果注入强度不够，就会在限速以下形成新的平衡点，看起来像“怎么都跑不到设定的限速”。
- 另外还存在两个代码层面会让“实际限速 < 你在 UI 里设置的限速”的高概率点：
  - VelLimit 单位换算：UI 以 km/h 输入，但写入 detour 时多数路径会做 Kmh→Mph 换算（KmhToMph），如果 detour/游戏侧实际期望的单位并不是 mph，就会天然“卡在更低的速度”。
  - 固定强度模式的开关初始化写 VelLimit 没有做换算，和循环内写入方式不一致，容易造成“刚打开/没重新按 RT 时表现不对”。

## 实施改动（让它“能跑到限速”）
1) 先做“单位与写入一致性修复”
- 把固定强度开关初始化写 VelLimit 改为 KmhToMph，与其它路径一致。
- 把固定强度循环从“首 tick 只写一次 limit”改为与线性/多段式一致的“降频写参数（100ms 或变化阈值）”，这样你按住 RT 时改限速会立即生效。

2) 增加可选的“追限（闭环）”策略（核心：从‘上限阈值’升级为‘目标速度控制’）
- 在三种模式共用的注入计算里加入一个可选项：根据当前速度与限速误差 e = (limitKmh - speedKmh)/limitKmh 计算额外 boost；接近限速时仍保留最小加成，避免无限趋近但到不了。
- 形式上提供两档：
  - 简单档：boostPerSec = 1 + clamp(kP * e, 0, maxDelta)
  - 稳定档（可选）：PI（带积分上限/抗 windup），提升“爬到限速”的确定性。

3) 诊断增强（不增加噪音，但能定位原因）
- 在高级诊断里加一行：speedKmh、limitKmh、error、最终 boostPerSec、boostTick、applyHz。这样能区分“单位错/写入没生效/强度不足/车物理上顶不动”。

## 验证方式（实现后马上自测）
- 用高级诊断确认：memVelLimit 与 UI 限速一致（同一单位链路）。
- 选一台动力弱的车与一台动力强的车：在相同限速下观察是否都能稳定爬到限速附近（允许 1-3 km/h 的浮动）。
- 改限速：按住 RT 时滑动限速，确认固定强度也能实时跟随。
