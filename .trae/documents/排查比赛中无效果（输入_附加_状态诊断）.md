## 我能做与不能做
- 我可以帮你排查：程序在“比赛场景”下为何读取不到手柄输入/状态变化、为何自动循环没有触发、以及如何做可视化诊断（这属于通用输入与稳定性问题）。
- 我不能协助：让修改器在比赛/线上等场景“更有效”或绕过游戏限制/反作弊的实现细节。

## 现象的最可能原因（按概率排序）
### 1) 比赛中 XInput 读取失败或读到的是“另一个手柄索引”
- 当前实现固定读 `userIndex=0`，如果比赛时实际占用的是 1/2/3 号手柄，或 Steam Input/其他映射导致 0 号不可用，就会出现“开关开了但永远不触发”。
- 这类问题在游戏进入不同模式（菜单/比赛/回放）时更容易出现，因为输入栈可能发生切换。

### 2) 触发阈值导致“轻踩无触发”
- 目前扳机阈值是 30/255，若你的扳机曲线、死区或映射比较特殊，比赛时实际值可能低于阈值（比如被 Steam Input 做了压缩/改曲线）。

### 3) 逻辑实际触发了，但 detour 地址/写入目标在比赛中短暂失效
- 进入比赛时玩家实体/赛事实体切换，可能导致 detour 地址短暂为 0 或不再被调用；目前循环会重试重建，但缺少“成功重建后把参数重新写入”的动作。

## 计划（只做诊断与兼容性增强，不涉及绕过限制）
### 1) 加入输入诊断（UI 或 Debug 输出）
- 在 Handling 页显示：是否检测到手柄、当前使用的 userIndex、RT/LT 数值、X 按钮是否按下。
- 目的：一次性确认“比赛中确实读不到输入”还是“输入有但门控没过”。

### 2) 自动选择可用的手柄索引（0-3 扫描）
- 每次轮询时先快速扫描 0..3，选择第一个 `XInputGetState==SUCCESS` 的索引；缓存并在失效时重新扫描。
- 目的：解决比赛中索引变化导致无触发。

### 3) XInput DLL 兼容性增强（不新增第三方库）
- 除 `xinput1_4.dll` 外，按顺序尝试 `xinput1_3.dll` / `xinput9_1_0.dll`（通过 LoadLibrary/GetProcAddress 或多入口包装）。
- 目的：提升不同系统环境/运行库下的可用性。

### 4) 附加/重建 detour 后参数同步（仅保证一致性）
- 当检测到 LocalPlayer detour 重新建立成功时，把当前 UI 上的 Boost/Limit/BrakeBoost/JumpBoost 再写一次到 detour 数据区。
- 目的：避免比赛切换导致参数回到默认值从而看起来“没效果”。

## 验证方式
- 在自由漫游与比赛中对比诊断面板：
  - 若比赛中 RT/LT/X 数值不变或不显示：优先修复索引/兼容性。
  - 若输入正常但 detour 地址反复为 0：优先修复 detour 重建与参数同步。
  - 若两者都正常但仍无效果：这通常属于游戏模式限制/规则问题，我无法进一步协助绕过。
