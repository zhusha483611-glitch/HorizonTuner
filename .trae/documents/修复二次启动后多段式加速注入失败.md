## 现象归因（基于代码）
- 你现在看到的“未获取到本地玩家地址”，触发点是 Handling 的开关事件里：调用 `CheatLocalPlayer()` 之后 `_carCheats.LocalPlayerHookDetourAddress` 仍为 0，于是弹窗并回滚开关。[Handling.Velocity.cs](../../MA_FH5Trainer/MA_FH5Trainer/Views/SubPages/SelfVehicle/Handling.Velocity.cs#L158-L249)
- `CheatLocalPlayer()` 返回 false 但不一定抛异常；其中一个常见的“静默失败”路径是 CRC 绕过地址没拿到（`bypass.CallAddress <= 3` 时直接 `return false`），UI 只会显示“本地玩家地址”那条提示。[CarCheats.CheatLocalPlayer](../../MA_FH5Trainer/MA_FH5Trainer/Cheats/CarCheats.cs#L44-L130)
- 更关键的是：当前“附加状态机”存在“假附加”的可能——`OpenProcess` 返回 `ProcessNotFound` 仍会继续执行 `GvpMaker` 并把 `Attached=true`，导致 UI 看起来已附加，但 `MProc.Handle/Process` 未必有效，AOB 扫描/写入就会失败（多段式最先暴露）。[MainWindowViewModel.SetupAttach](../../MA_FH5Trainer/MA_FH5Trainer/ViewModels/Windows/MainWindowViewModel.cs#L320-L362)

## 修复目标
- 避免“Attached=On 但实际没拿到有效句柄/进程”的状态。
- 让多段式加速在重新打开程序后能够稳定再次注入并生效。
- 让失败提示可定位（区分：未附加/句柄无效、CRC patch 失败、RacePtr 失败、Hook 签名未命中、Detour 分配失败）。

## 实施步骤（将会修改的点）
1) 修正附加状态机（核心）
- 在 `SetupAttach()` 中：只有 `OpenProcessResults.Success` 才允许 `GvpMaker()` + `Attached=true`；`ProcessNotFound` 视为未附加（继续闪烁红灯/保持 Off）。
- 在 `Attached==true` 分支里：除了检查“进程是否存在”，还校验 PID 是否变化、以及当前句柄/进程是否仍有效；若失效则强制走一次重新 `OpenProcess`，并对所有 cheats 做 `Reset()`。
- 进程消失（或判定失效）时：补充 `CloseHandle(MProc.Handle)`，避免持有失效句柄。

2) 多段式注入流程做结果判定与更细错误提示
- `VelocityMultiStageSwitch_OnToggled`：改为读取 `bool ok = await _carCheats.CheatLocalPlayer()`，并根据失败原因给出更明确的中文提示（至少把“未附加/句柄无效”与“CRC patch 失败”分开）。
- 同步把“注入失败”时的状态回滚逻辑保持不变（避免 UI 卡住）。

3) 让自动维持逻辑在“句柄失效/未附加”时不做无意义重试
- `EnsureLocalPlayerDetourAsync`：在尝试重建 detour 前，加一层对“当前是否真正已附加（句柄有效）”的判定；无效则快速返回，等待附加成功后再继续。

## 验证方式
- 场景 A：游戏已在驾驶场景 → 启动训练器 → 开启多段式 → 确认生效。
- 场景 B：关闭训练器 → 立即再次启动 → 不重新开游戏 → 再次开启多段式 → 确认不再报“未获取到本地玩家地址”。
- 场景 C：训练器启动时游戏未运行/刚启动中 → 确认不会出现 Attached=On 的假状态；待游戏可附加后自动变为 On。
- 场景 D（回归）：确认退出程序仍不崩溃、手柄状态轮询正常。

## 影响范围
- 主要影响附加/断开状态机与 Handling 注入体验；不改变各类 cheat 的 AoB 签名与核心写入逻辑。
